# Substrate's own API (`kubectl ate`) on GCD, and the principal it needed
# kagent 1.0.0-alpha16 / Substrate 0.6.0-alpha3, cluster agentic (eu0:soloio-eval), 2026-10-21
# kubectl-ate built from kagent-dev/substrate tag v0.6.0-alpha3 (git archive, go 1.27.1): scripts/lib.sh ate_cli

How ate-api-server checks a caller (cmd/ateapi/internal/apiauthn, authz):
  authentication: a client certificate's SPIFFE ID (mTLS), else a bearer JWT from a configured issuer.
    ConfigMap ate-api-authentication: one provider, the cluster's own issuer
    https://container.apis-berlin-build0.goog/v1/projects/eu0:soloio-eval/locations/u-germany-northeast1/clusters/agentic,
    audience api.ate-system.svc. A ServiceAccount token authenticates as system:serviceaccount:<ns>:<name>.
  authorization: OpenFGA; bootstrap owners always hold owner on global:root.
    kagent install sets --authz-bootstrap-owners=spiffe://cluster.local/ns/kagent/sa/kagent-controller (only).

1. No --token-file (kubectl ate mints a token for the shared ate-system/ate-client account):
   Warning: no --token-file given; acting as the shared identity system:serviceaccount:ate-system:ate-client rather than as yourself. Pass --token-file to act as yourself.
   Error: failed to list atespaces: rpc error: code = PermissionDenied desc = permission denied: principal "user:system%3Aserviceaccount%3Aate-system%3Aate-client" lacks "can_list_atespaces" on "global:root"

2. --token-file with a kagent-controller ServiceAccount token (kubectl create token kagent-controller -n kagent --audience api.ate-system.svc):
   Error: failed to list atespaces: rpc error: code = PermissionDenied desc = permission denied: principal "user:system%3Aserviceaccount%3Akagent%3Akagent-controller" lacks "can_list_atespaces" on "global:root"
   (the token authenticates, but as system:serviceaccount:kagent:kagent-controller; the owner is the controller's
   Pod Certificate SPIFFE ID, which only an mTLS client certificate carries)

3. Fix: an explicit operator principal (Substrate's own advice: never ate-client outside development)
   yaml/ate-operator.yaml       ServiceAccount ate-system/ate-operator
   yaml/substrate-values.yaml   ateApi.authorization.bootstrapOwners:
                                  - spiffe://cluster.local/ns/kagent/sa/kagent-controller   (kept: a values file replaces kagent's list)
                                  - system:serviceaccount:ate-system:ate-operator
   helm template diff, old vs new values: exactly one line, ate-api-server's
     --authz-bootstrap-owners=...kagent-controller  ->  ...kagent-controller,system:serviceaccount:ate-system:ate-operator
   atelet DaemonSet unchanged (generation 1 before and after), so its WorkloadAllowlist stands.

4. The upgrade, and a GCD finding on the way
   helm upgrade substrate (revision 2): FAILED
     server-side apply failed for object ate-system/rustfs-bucket-init batch/v1, Kind=Job:
     Job.batch "rustfs-bucket-init" is invalid: spec.template: ... field is immutable
   cause: Autopilot raised the bucket Job's CPU request from the chart's 10m to its 50m minimum when the Job was
   created; every later apply re-submits 10m into the completed Job's immutable pod template. Any upgrade of the
   substrate release, including a re-run of `kagent install`, fails this way on Autopilot.
   fix: yaml/substrate-values.yaml sets rustfs.bucketInit.resources to exactly what Autopilot stores
        (requests cpu 50m, memory 128Mi, ephemeral-storage 1Gi; limits cpu 500m, memory 256Mi, ephemeral-storage 1Gi)
   helm upgrade substrate (revision 3): deployed, "Upgrade complete"; ate-api-server rolled out with the new flag.
