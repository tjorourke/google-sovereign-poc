# Reply to Google — 1.36 re-test: ComputeClass confirmed, root cause is GPU quota

**Date:** 2026-09-11
**To:** Alfred Chung, and the engineer investigating
**Evidence:** `feedback/google/evidence/berlin-computeclass-136-retest-2026-09-11.txt`

---

Hi Alfred,

Tested on 1.36 as asked. **Your engineer is right, and the ComputeClass finding
is resolved.** It also moved us past the CRD to what looks like the real
blocker, which is a quota gap rather than a GKE one.

We destroyed the 1.35.6 cluster and rebuilt on `1.36.0-gke.4681000` in RAPID —
we could not run both, because `C3_CPUS` is 24 in this project and the first
cluster consumed all of it. Same project, same universe, so the only variable is
the GKE version.

## 1. ComputeClass is served on 1.36. Confirmed.

```
$ kubectl api-resources --api-group=cloud.google.com
NAME             SHORTNAMES   APIVERSION            NAMESPACED   KIND
backendconfigs   bc           cloud.google.com/v1   true         BackendConfig
computeclasses   cc,ccs       cloud.google.com/v1   false        ComputeClass
```

Absent on `1.35.6-gke.1049000` REGULAR, present on `1.36.0-gke.4681000` RAPID.
Exactly as your engineer found. A ComputeClass with a GPU priority rule applies
cleanly and reports `Crd is healthy`, and Warden no longer rejects a GPU pod.

Please treat that as answered and closed from our side. One small ask attached
to it, below.

## 2. `machineFamily: a3` is not enough — the machine type has to be explicit

Worth recording because it cost us a cycle. A ComputeClass with:

```yaml
priorities:
  - machineFamily: a3
    gpu: { type: nvidia-h100-80gb, count: 8 }
```

never triggers a scale-up: `NotTriggerScaleUp: 3 node(s) didn't match Pod's node
affinity/selector`. Changing only that one field to:

```yaml
priorities:
  - machineType: a3-edgegpu-8g-nolssd
    gpu: { type: nvidia-h100-80gb, count: 8 }
```

**does** trigger one. That matches the note in the GKE differences page about A3
Edge needing to be requested explicitly, but the `machineFamily` failure is
silent and looks identical to the 1.35.6 behaviour, so it is easy to conclude
nothing has changed when it has.

## 3. The new failure: scale-up is attempted, then refused on quota

This is the useful part. On 1.35.6 the autoscaler never tried. On 1.36 it does:

```
Normal   TriggeredScaleUp   Pod triggered scale-up:
  [{...instanceGroups/nap-1f4zkot9-temporary-mig-xdtm6vl1-async-0 0->1 (max: 1000)}]
Warning  FailedScaleUp      Node scale up in zones u-germany-northeast1-a
  associated with this pod failed: GCE quota exceeded.
  Pod is at risk of not being scheduled.
```

So the mechanism works end to end now. It stops at quota.

## 4. Root cause: the only GPU offered here has no quota metric

`nvidia-h100-80gb` is the sole accelerator type in the catalogue, in both zones:

```
$ gcloud compute accelerator-types list --filter='zone~u-germany-northeast1'
NAME              ZONE
nvidia-h100-80gb  u-germany-northeast1-a
nvidia-h100-80gb  u-germany-northeast1-b
```

But the region's GPU quota metrics are, in full:

```
NVIDIA_A100_80GB_GPUS   NVIDIA_A100_GPUS   NVIDIA_K80_GPUS   NVIDIA_L4_GPUS
NVIDIA_P100_GPUS        NVIDIA_P100_VWS_GPUS   NVIDIA_P4_GPUS   NVIDIA_P4_VWS_GPUS
NVIDIA_T4_GPUS          NVIDIA_T4_VWS_GPUS     NVIDIA_V100_GPUS
```

Grepping the region's quotas for `H100` or `A3_` returns **nothing**.

So every GPU that has a quota metric here is one the universe does not offer,
and the one GPU it does offer has no metric at all. The effective H100 limit is
zero, and because there is no metric, there is nothing for us to request an
increase against — the quota page has no row to raise.

That reads like the inherited public-GCP quota list has not been reconciled with
Berlin's actual hardware catalogue.

## What we are asking for

1. **Create the H100 / A3 quota metrics for this universe** — presumably
   `NVIDIA_H100_80GB_GPUS` and whatever the A3 CPU metric is called — and give
   `eu0:soloio-eval` a non-zero limit. Eight H100s, i.e. one
   `a3-edgegpu-8g-nolssd`, is enough for everything we need to demonstrate.
2. **Confirm the intended GA behaviour for ComputeClass.** It is in RAPID 1.36
   today and absent from REGULAR 1.35.6. Customers following Google's GCD AI
   reference architectures will be on the channel default, so if ComputeClass is
   required for A3 it needs to reach REGULAR before GA, or the blueprints need to
   say "RAPID only" out loud.
3. **A docs fix, small and cheap.** The GKE differences page says Stable and
   Regular channels only. `gcloud container get-server-config --location
   u-germany-northeast1` returns a RAPID channel with `1.36.0-gke.4681000` as its
   default. We had encoded "no RAPID" as a Terraform validation rule on the
   strength of that page, which is precisely the channel we needed to test on.

Happy to keep this cluster on 1.36 RAPID and re-run the moment a quota lands —
the whole stack rebuilds from one script, so testing for you is cheap.

## Why it matters for an ISV

Berlin has no `aiplatform`, so in-universe inference is self-hosted by
definition, and Google's own GCD reference architectures answer that with
open-weight Gemma on GKE using A3/H100. We are currently serving a 3B model on
CPU because it is the only thing that will schedule. That is fine for a
functional demo and not fine for a customer benchmark. Any ISV following the
published GCD AI blueprint meets this on day one — and with the CRD now fixed in
1.36, quota is the last thing standing between the blueprint and working.
